# AGENTS.md

Instructions for AI agents (and developers) working in this repo. Human-facing docs live in `README.md`. This file is the **normative spec**: if the code and this file disagree, fix one of them so they match, and say which one you changed.

## What this repo is

`planner.py` parses a plain-text planning-notes format and prints five views: `projects`, `timeline`, `people`, `upcoming` and `week` (the page calls the last one the **Planner**: year, season, month or week). `planner.py` uses only the Python standard library (3.8+). It also serves a small web page (`web/index.html`, `web/app.css`, `web/app.js`) with `--serve`, for the **portfolio** of projects in the `Projects` folder next to `planner.py` (`PROJECTS`), or one notes file (`--serve notes.txt`); the CLI views read a portfolio folder too. `Projects/Example` is the sample project users see. `example.kf` is the reference input and exercises every rule; `example/` is the reference portfolio for the tests (`example.kf` split into projects, plus sample pages). `example.txt` is not a reference: the user keeps their own notes there, so tests never read it.

## Ground rules

1. **The note format belongs to the user.** It is a light layer over how they already write notes. Do not add, rename or repurpose markers unless the user asks. Propose format changes in plain words first.
2. **Keep it stdlib-only.** No `pip` dependencies, in Python or in the page (no CDN scripts, no JS libraries). Parsing lives only in `planner.py`; the page never re-implements the note format, it asks the server. Keep the repo small: `planner.py`, `web/index.html` + `web/app.css` + `web/app.js`, `test_planner.py`, the docs, `changelog.txt`, `example.kf`, `example/` and `Projects/Example` (the rest of `Projects/` is the user's and git-ignored).
3. **Parsing never changes the notes.** The tool edits them only on an explicit user action (clicking a task's status box, its title, or its Who / Effort / Date / + / ⋯ cells, + Add task, or Archive done). An edit touches only its target line and only the characters it must; adding a subtask or task inserts one new line and changes no existing line (except giving a final line with no line ending one); deleting a task removes exactly its lines and its subtree's (subtasks and notes) and nothing else; archiving moves those lines, wording unchanged, into the archive file (only the task's own indentation is taken off), and the archive file is written before the lines leave the source. Wording, order, indentation, trailing whitespace and line endings stay exactly as they were. An edit made from an out-of-date view is refused, not guessed at. When you edit or generate notes for the user, follow the grammar below exactly and preserve the same things.
4. **Keep `README.md` (humans), this file (machines) and the docstring at the top of `planner.py` in sync** whenever behaviour changes, and add an entry at the top of `changelog.txt` (current series: 2.0.x; bump the patch number for each change unless the user picks another version). A new view or field must reach `to_data` and the page (`web/app.js`) as well as the CLI.
5. **Verify every change** by running the commands in [Testing](#testing).

## Format specification

### Lexical

- Input is UTF-8 text, processed line by line. Blank or whitespace-only lines are ignored.
- **Indent level** = (number of `\t` in leading whitespace) + floor(number of spaces in leading whitespace / 4).
- `content` = the line with leading and trailing whitespace stripped.

### Line classification

Rules are checked **in this order**, and the first match wins:

| # | Condition on `content` | Kind | Effect |
|---|---|---|---|
| 1 | starts with `@` | **project** | New project named `content[1:].strip()`, inside the current section. Clears the task stack. |
| 2 | starts with `--` | **note** | Appended to the most recent task (top of the stack). If there is none, it attaches to the current project. Indent is ignored. |
| 3 | matches `^(\(!\))?([!~]?)-\s*(.*)$` (`RE_TASK`) | **task** | `(!)` first = **notable** (circled in purple; any status). Status: `!` = done, `~` = doing, none = open. Parent = nearest earlier task on the stack with a strictly lower indent level. |
| 4 | indent level == 0 | **heading** (section) | New section. Its text is parsed for dates the same way tasks are. Clears the current project and the task stack. |
| 5 | otherwise (indented free text) | **note** | Same as rule 2. |

A task that appears before any `@` line goes into an implicit project named `(no project)`.

### Inline tokens (tasks and headings)

These are extracted in this order. Each token is removed from the text, and whatever remains (whitespace collapsed) is the title.

| Token | Regex (MON = `Jan\|Feb\|…\|Dec`, case-sensitive) | Field |
|---|---|---|
| Effort | `(?<!\w)\(\s*(xs\|s\|m\|l\|xl)\s*\)` (lowercase only) | `effort` (`xs`/`s`/`m`/`l`/`xl`) and `points` (1/1/3/5/8, `EFFORT`) (first match only) |
| Assignees | `\(\s*([A-Z]{1,4}(?:\s*,\s*[A-Z]{1,4})*)\s*\)` | `assignees` (all matches) |
| Reminder | `\*(daily\|weekdays\|weekly\s+[A-Za-z]{3}[a-z]*(?:\s*,\s*DAYNAME)*\|monthly\s+\d{1,2}(?:st\|nd\|rd\|th)?\|MON\d{1,2})\b` (DAYNAME = `Mon`…`Sun`, either case, then any lowercase letters) | `reminders` (all matches). A repeating one (`repeats`: not a one-off `*Oct13`) is a habit's frequency |
| Priority | `(?<!\S)\^(wk\d{1,2}\|MON\|T[1-3]\|yr)\b` (`RE_PRIO`) | `priorities`: `[(token, kind, start, end)]`, every valid match: a top priority for that week, month, trimester or (`^yr`) TODAY's year (`priority_of`; resolved like loose dates). Invalid ones (`^wk54`, `^T4`) stay in the title |
| Plan | `(?<!\S)>(?:(MON)(\d{1,2})\|wk(\d{1,2})\|(MON)\|(T[1-3]))\b` (`RE_PLAN`) | when the task is planned for (first valid match only; `plan_of`): a day `>Oct14` (resolved like a single date), a week `>wk45`, a month `>Nov` or a trimester `>T3` (resolved like the loose dates). Sets `plan` (start), `plan_end`, `plan_kind` (`day`/`week`/`month`/`season`) and `plan_token`. Not a date: it doesn't change `start`, `end`, `span` or overdue |
| Range | `(?<![\w*~>])(MON)(\d{1,2})--(MON)?(\d{1,2})\b` | `start`, `end` (first match only) |
| Loose date | `(?<!\S)~(Q[1-4]\|T[1-3]\|wk\d{1,2}\|MON)\b` | `start`, `end`, `loose` (only if no range was found) |
| Date | `(?<![\w*~>])(MON)(\d{1,2})\b` | `start = end` (only if neither of the above was found) |

Each task has at most one date span, one effort and one plan. Later date, effort or plan tokens on the same line stay in the title (a leftover `>Oct14` is never read as a date). Effort is taken first, so removing initials can't glue it to a word; `file(s)` (no space before) is not effort, and `(S)` / `(XL)` are initials.

### Date resolution (no years are ever written)

`TODAY` defaults to `date.today()`. Set it with `--today Oct12` or `--today 2026-10-12`. Set `PAST_DAYS = 90`.

- **Single date `MonDD`:** the unique year *y* in {TODAY.year−1, TODAY.year, TODAY.year+1} such that `TODAY − 90d ≤ date < TODAY − 90d + 365d`. If no valid date exists (for example `Feb30`), the token is ignored and stays in the title.
- **Range end:** the first occurrence of the end month and day **on or after** the resolved start. If the end month is omitted, it is the start month. `Dec15--Jan10` crosses the year correctly.
- **Loose `~Q1` / `~T1` / `~Nov` / `~wkNN`:** the earliest candidate period (quarter; trimester, the same months as the seasons in calendar order: `T1` Jan–Apr (Winter), `T2` May–Aug (Summer), `T3` Sep–Dec (Fall), from `SEASONS`; calendar month; or ISO week Mon–Sun), across those three years, whose end is `≥ TODAY − 90d`.
- **One-off reminder `*MonDD`:** resolved like a single date. Its next-fire date is `None` if it is before TODAY.
- **Repeating reminders:** `daily` fires every day, `weekdays` Monday to Friday, `weekly Ddd` (or `weekly Mon, Wed, Fri`) on those weekdays, `monthly N` on day N (skipping months without it). The next one is the first such day ≥ TODAY (`reminder_days`, `next_reminder`).
- **Habit log** (a note `-- done Nov02 Nov03` under a task; `log_of`, `Task.log()`): each `MonDD` is the **latest such day on or before TODAY** (`resolve_past`; on an archive page, on or before Dec 31 of its year, `LOG_END`). A note `done` followed by anything else (`done with Lisa`) is an ordinary note. Log notes aren't listed as notes in the views.

### Derived semantics

- `rollup(task)` = (min start, max end) over the task and all its dated descendants.
- `span(task)`:
  1. If the task has its own dates, return `rollup` and mark it `own`. This means a parent's span **stretches** to cover its children.
  2. Otherwise, if any descendant is dated, return `rollup` and mark it `rollup`.
  3. Otherwise, return the own dates of the nearest dated ancestor and mark it `parent` (inherited).
  4. Otherwise, return `None`, which means the task is **unscheduled**.
- **Overdue** = status ≠ done, and span is not `None`, and span end < TODAY.
- **Assignees are not inherited.**
- **Effort is not inherited and does not roll up.** A task without its own token has 0 points. `effort_points(tasks)` = (points of tasks not done, all points), a simple sum of each task's own points. Projects show it over all their tasks (ignoring the period, like the done count); people show the not-done sum of their listed tasks.
- Section (heading) dates are display-only. Tasks do not inherit them.

### Valid-note checklist (for agents writing notes)

- Every task line starts with `- `, `~- ` or `!- ` after its indentation, optionally with `(!)` in front for a notable task: `(!)- `, `(!)~- `, `(!)!- `.
- Subtasks are indented exactly one more tab than their parent.
- Notes start with `-- ` and go directly under the task they describe.
- Dates are `MonDD` with no space (`Oct24`, `Nov03`). Ranges are `Oct23--26` or `Oct23--Nov03`. Loose dates are `~Q1`, `~T1` (trimester: T1 Winter Jan–Apr, T2 Summer May–Aug, T3 Fall Sep–Dec), `~Nov` or `~wk43`.
- A plan is `>Oct14` (a day), `>wk45`, `>Nov` or `>T3`, with a space before it, after the date and before any priority and reminder: `draft report (KA) (m) Oct24 >Oct14 ^wk42 *Oct13`.
- A top priority is `^wk45`, `^Nov`, `^T3` or `^yr` (this year), after the plan; a task can have several. It says when you mean to work on the task; the date stays the deadline.
- Initials go in parentheses: `(KA)` or `(KA, RT)`.
- A habit (in a project's `habits.kf`) is a task with a repeating reminder: `- stretch *daily`, `- gym (KA) *weekly Mon, Wed, Fri`, `- standup *weekdays`, `- rent *monthly 1st`. The days it was done go in one note directly under it: `\t-- done Nov02 Nov03`.
- Effort is `(xs)`, `(s)`, `(m)`, `(l)` or `(xl)`, lowercase, with a space before it. Write it after the initials and before the date: `finish proposal (KA) (m) Oct24`.
- Never write years. Never put free text at the left edge unless it is meant to be a heading.

- **Planner** (`vPlanner`; the tab was **Week** before 2.0.3 and a stored `week` tab becomes `planner`): in the tool row, instead of the period control, **Year / Season / Month / Week** (`wSeg`; the level is remembered as `planKind`) and `‹ Oct 12-18 ›` (`wctl`; `state.plan`, sent as `planner`; the period itself is not remembered, so the Planner opens on the current one; the middle returns to it, accent-coloured when away). A wider content column (`.content.wide`). The context line says "Drag a task onto a day (week, month, trimester), or use its Plan cell · ☆ marks a top priority for this week". From the top: **On the calendar** (`projectChips`): a chip per project with × to take it off, and **+ Add project** (a select of the ones taken off; **Show all** when more than one is off); remembered as the ones taken off (`plannerHidden`), so a new project shows by itself; in a portfolio the chips are the project folders, otherwise the `@` projects; hidden only with fewer than two. **Top priorities** (`.wprio`): the tasks marked for exactly this period, or a hint. The **columns** (`.wdays`, as many as the level has, `--ncols`; today's is tinted, "now"; a column whose token can't reach it is hatched, `.off`, and takes no drops) with a card per task (`weekItem`: status, ☆, title, `@project · effort`, and the plan when it is finer than the column, like `Oct 14` in a month's week); **This week / month / season / year** (`.wside`; or the period's label when not the current one): the planned tasks per project with where (`Mon`, or `plan_label`) and the points done of those planned, `4/16 pts` (`sumPts` of the done ones / of all; follows the filters). Below: **Starred first** (2.0.9): a task starred for the period shown comes first in its column, in its side-panel group (and those groups first), and in the backlog, where it moves to the top of its project with its subtasks under it (`starFirst`, `starBlocksFirst`, `groupsStarFirst`; display order only). **Backlog**, every open task not planned for the period, as `taskNode` rows with a ☆ before the title and a **Plan** cell instead of **+** (`week` option; it shows `plan_label` for a task planned elsewhere or coarser). **Planning:** drag a card or a backlog row's title side onto a column (`draggable`, `dropZone`), between columns, or onto the backlog to unplan; or click a card, a line or a Plan cell for the column list (`planPick`: the plannable columns, "now" on the current one, and Unplan with the current plan). All go through op `plan` with the column's `token` (`planTask`). **☆** (`starButton`) toggles op `priority` with `planner.star.token` (`-` in front to remove); disabled with a reason when the period can't be marked (`star.ok` false: too far away, or a year other than this one). Everything gets the toast and Undo. With Edit alongside a card click jumps to the line instead. Under 900px the side panel goes below the columns; under 560px the columns stack; in a narrow pane the Plan cell always shows (phones can't drag). Filters and the project chips apply to all of it (`filtered` covers `planner`). **Habits in the Planner** (`habitsIn`, a portfolio's `habits.kf` files): on the Week level each day column lists the habits due that day (or done) with a tick box (the Sat/Sun column says which day); on the other levels each column says `Habits: N of M done`. In a portfolio the Planner is one page for every project: the drawer's first entry (**Planner**, above All projects), and the Planner tab on a project page opens it (`showAll` with tab `planner`); the breadcrumb says "Planner". An empty Planner (no notes) shows the welcome.

To add a view, write `view_x(projects) -> list[str]`, register it in `VIEWS`, and document it in both READMEs.

## Design notes: weekly planner (the Planner since 2.0.3)

Agreed with the user; change only with them:

- **Four levels (2.0.3):** Year (trimester columns), Season (months), Month (Mon-Sun weeks), Week (days). Each plans into its columns with `>T3`, `>Nov`, `>wk45`, `>Oct14`; a plan rolls up into the larger periods that contain it. One Planner for every project in a portfolio, with project chips to choose which are on the calendar (the user's request).
- **Top priorities (2.0.3):** a ☆ marks a task for the period shown (`^wk45`, `^Nov`, `^T3`, `^yr`); several per task are fine. `^yr` can only mean this year (a yearless token can't name another).
- **The plan lives in the notes**, as `>MonDD` in the task's line: the notes stay the single source of truth, it works in any browser, and it's editable by hand. It is separate from the date, so "due Oct 24, work on it Tuesday" can be written.
- **Six columns:** Monday to Friday, then Saturday and Sunday together (planning to the weekend writes Saturday's date).
- **The project sum is effort points only** (the user's choice), over the tasks planned that week, done ones included.
- **No automation:** an unfinished task planned for a past day stays there; next week it is back in the backlog with its old plan shown. No times of day, capacity limits or recurring plans (habits come separately).
- **Two ways to plan, one edit:** drag and drop for the mouse, the day list for touch and keyboard; both are the `plan` op.

## Design notes: portfolio (2.0)

Agreed with the user (Nov 2026); change only with them. The file tabs and browser-kept Quick note that came before were removed in 2.0.8 (the user's choice), leaving the portfolio and `--serve notes.txt`.

- **The portfolio is one folder, `Projects`, next to `planner.py`; a project is a sub-folder (2.0.7, the user's choice).** A plain `python planner.py --serve` finds it, or makes it if it's missing; there is no way to serve or choose another folder (`--serve FOLDER` and the drawer's portfolio choices of 2.0.6 are gone). Only `--serve notes.txt` (one command-line file) has no drawer. Git ignores `Projects/` except the sample `Projects/Example`. The project's name is its folder name. No database and no index file: the files are the only copy, they stay editable by hand, and any folder-sync tool can sync them.
  ```
  Projects/                  portfolio
    HDC/                     project
      backlog.kf             the planning document (kafeen format)
      quicknote.kf           the project's quick note (on disk)
      habits.kf              repeating tasks
      notes/                 pages (.kf, .txt, .md); one level of sub-folders = sections
        Kickoff call.md
        Client/Requirements.kf
      archive/2026.kf        finished tasks, one file per year
    .trash/                  deleted projects and pages are moved here, never removed
  ```
  **+ New project** makes these as empty placeholders, with the `notes/` and `archive/` folders (2.0.7, the user's choice); a folder added by hand gets its files on first write. Hidden (dot) files and folders are never listed.
- **`.kf` marks the kafeen format.** The grammar is the same. A Backlog, Archive year or Habits page opens in Planner mode; every other page opens in Markdown if it is a `.md`, else in Text, with Planner greyed out (2.0.8; derived from the path, not a per-file setting).
- **In a backlog, tasks before any `@` belong to the project itself** (shown under the project's name, not `(no project)`); `@` lines inside it are sub-groups (workstreams).
- **Side drawer** (click the KAFEEN logo): **Planner** (all projects), **All projects** (the existing views over every backlog), then the project list (search, + New project). A selected project shows Quick note, Backlog, Notes (sections fold, pages listed, like OneNote), Habits and Archive (by year). The header shows a breadcrumb (`MDM › Notes › Kickoff call`) instead of file tabs. Every page autosaves (`AUTOSAVE_MS`). Rename and delete sit in a `⋯` on each drawer row; delete moves to `.trash`.
- **No portfolio-wide quick note** (the user's choice); the project quick notes live on disk.
- **Edits are made by the server on the file** when a view spans files: `{path, version, line, title, op, value}`; the server reads the file, applies the usual edit function, refuses a stale version, and writes atomically. The page flushes its autosave first so the text box and the disk can't disagree.
- **The page is split** into `web/index.html`, `web/app.css` and `web/app.js` (the user's choice, 2.0.0); still no dependencies.
- **Migration:** `planner.py --import notes.txt` makes one project from a file (its lines copied unchanged into `backlog.kf`); with `--split` each `@` group becomes its own project (the section heading above it is copied too, so nothing is lost).

**Format additions of 2.0 (all built; the rules are in the Format specification):** notable `(!)` (2.0.2; drawn as a purple box around the row, in every view and in the archive; separate from priority), plans to a week, month or trimester (`>wk45`, `>Nov`, `>T3`) and top priorities (`^wk45`, `^Nov`, `^T3`, `^yr`; set with a ☆ in the Planner, never typed by the page) (2.0.3), and:

- **Habits (2.0.4):** `habits.kf`, ordinary tasks whose repeating reminder is the frequency: `*daily`, `*weekdays`, `*weekly Fri`, `*weekly Mon, Wed, Fri`, `*monthly 1st`. Ticking a habit for a day appends the date to a log note under it: `-- done Nov02 Nov03`; log dates mean the latest such day so far, so a day not yet come can't be ticked. Last year's ticks move to the archive (`@Habits` in `archive/YEAR.kf`) on the user's click. A retired habit is marked done (`!-`).
- **Archive (2.0.2):** `archive/YYYY.kf`, same format; a task moves there with its subtasks and wording, under the same `@` group (the project's own tasks stay before any `@`). It is parsed with TODAY anchored so its dates fall in that year (`archive_today`: Jan 1 + 90 days). **Archive done** takes a project's finished top-level tasks only (done, with every subtask done); a done subtask of an unfinished task stays with it (it can still be archived on its own from its ⋯).

**Planner levels** (built in 2.0.3; all projects together; the Week tab became this):

| Level | Columns you plan into | Token written |
|---|---|---|
| Year | T1, T2, T3 | `>T3` |
| Season | its 4 months | `>Nov` |
| Month | its Mon-Sun weeks | `>wk45` |
| Week | Mon-Fri, Sat/Sun together (unchanged) | `>Oct14` |

The backlog panel lists every project's open tasks not planned inside the shown period. Habits due in the period show in its cells with their own tick box (Week level) or as a count (the others). Project chips choose which projects are on the calendar.

- **The CLI reads a portfolio too (2.0.5):** `python planner.py ./Projects [views]` runs the views over every project's backlog (a sub-group reads `HDC · Stream`), and `week` lists each day's habits. Editing stays in the page.

### 4. `check` view: warnings for likely mistakes (next)

The parser silently ignores what it doesn't understand: the text just stays in the title, or a line becomes something the user didn't mean. `check` lists those places with line numbers. It only reads; it never fixes anything itself.

- **Code:** `check(text) -> list[(line, code, message)]` in `planner.py`. It walks the raw lines with the same classification as `parse` and compares them with the parse result (line numbers come from `Task.line`). It must reuse the `RE_*` constants and `parse` rather than define a second grammar; new regexes are only for the near misses below. `view_check` prints it, `VIEWS` gets `check`, and `to_data` gets a `check` list. The CLI view needs the text as well as the projects, so `main` passes it.
- **Warnings** (code: example → message):
  - `date-space`: `Oct 24` → "a date has no space: Oct24".
  - `date-spelling`: `oct24`, `Sept5`, `October24` → "months are Jan…Dec, capitalised: Oct24".
  - `bad-date`: `Feb30`, `Oct32` → "no such date; it stays in the title".
  - `extra-date`: a second date token left in the title → "only the first date on a line counts".
  - `backwards-range`: `Oct26--20` (resolves to next year) → "the range ends before it starts".
  - `bad-loose`: `~Q5`, `~wk54`, `~ Nov` → "loose dates are ~Q1-4, ~T1-3, ~Jan…Dec, ~wk1-53". (`~T4` too.)
  - `bad-reminder`: `*weekly Fry`, `*monthly 32nd`, `*tomorrow` → "this reminder never fires".
  - `bad-initials`: `(ka)`, `(KAREN)` → "initials are 1-4 capital letters". Must not flag the effort tokens `(xs)`, `(s)`, `(m)`, `(l)`, `(xl)`.
  - `bad-effort`: `(xxs)`, `(xxl)`, `(med)`, or a second effort token → "effort is (xs), (s), (m), (l) or (xl), once per task".
  - `skipped-level`: a subtask indented two or more levels below its parent, or an indented task with no parent → "indent one tab per level".
  - `missing-dash`: a left-edge line with no marker that has initials or a date, or a heading followed directly by tasks with no `@project` (they land in `(no project)`) → "this became a heading; did you mean `- …`?"
  - `dash-lookalike`: a line starting with `–`, `—` or `•` → "only `-` marks a task".
  - `orphan-note`: a note before any project or task → "this note has nothing to attach to".
- **Web page:** a fifth tab, "Check (N)". Clicking a warning opens Edit alongside and selects that line in the text box (`goToLine`).
- **Tests:** one per warning; `example.kf` must produce no warnings (it is the clean reference, so the bad cases live in the tests, not in `example.txt`).
- **Later, with the user's agreement:** a "fix" button per warning, done as one more `/api/edit` op under rule 3.

### 5. Calendar export (`.ics`)

`python planner.py notes.txt --ics plan.ics`, plus a download button on the page: one event per dated open task (all-day; a range spans its days; a loose date spans its period, marked "sometime in"), and reminders as events, with `*daily`, `*weekly Fri` and `*monthly 1st` as repeating events (`RRULE`). Each event's `UID` comes from project + title so re-importing updates rather than duplicates. Stdlib only (`.ics` is plain text).
